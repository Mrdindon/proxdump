# Encryption

[← proxdump](../README.md)

proxdump does not implement cryptography itself: every file is encrypted by
the [`crypt` backend of rclone](https://rclone.org/crypt/), on the server,
before anything is sent. This page describes what that means in practice.

## In short

| | |
|---|---|
| Contents of the files | Encrypted and authenticated: XSalsa20 cipher with a Poly1305 authenticator (NaCl *secretbox*) |
| Key | 256 bits, derived from the passphrase with scrypt |
| File and folder names | **Not encrypted**: the original name followed by `.encrypted` |
| Where encryption happens | On the Proxmox VE node; the destination never sees the passphrase or the plaintext |
| Passphrase | The same for every destination; stored on the node, to be kept elsewhere as well |

## Contents of the files

Each file is encrypted independently:

- a random 24-byte nonce is generated for the file and written in its
  header, after the 8-byte marker `RCLONE\0\0`;
- the data is cut into blocks of 64 KiB, each encrypted with **XSalsa20**
  and followed by a 16-byte **Poly1305** authenticator; the nonce is
  incremented from one block to the next.

The authenticator makes the encryption *authenticated*: a block that was
modified, truncated or moved on the destination is detected when it is read,
and the read fails instead of returning altered data.

The size overhead is 32 bytes per file plus 16 bytes per 64 KiB, about
0.025 %: a 10 GB archive grows by roughly 2.5 MB.

## The key

The key is derived from the passphrase with **scrypt** (N = 16384, r = 8,
p = 1). rclone allows a second passphrase to be used as the salt of that
derivation; proxdump does not set one, so rclone's built-in salt is used.
Two consequences follow:

- the same passphrase always gives the same key. This is what makes
  recovery possible on a new server, or with rclone alone, from nothing
  more than the passphrase (see [Disaster recovery](RECOVERY.md));
- the security of the backups rests entirely on the passphrase. The one
  generated by the tool is 33 random bytes (264 bits) written in base64,
  which is out of reach of any guessing attack. If you enter your own,
  choose a long one: a short or common passphrase could be searched for by
  someone who obtained the encrypted files.

## What stays visible

The file and folder names are deliberately left in clear, so that the
backups remain identifiable in the web interface of the provider and can be
sorted out without this tool. Whoever can browse the destination therefore
sees:

- the folder of the node and of each guest: its ID and its name
  (`pve-backups/<node>/100_web/`);
- the name of each archive, which contains the type of guest, its ID and the
  date and time of the backup;
- the size of each file (that of the archive, to within the overhead above)
  and the time it was uploaded.

The contents of the archives, including the configuration of the guests that
`vzdump` stores in them, and the contents of the `.log` files are encrypted.

If the names of your guests are sensitive, rename the guests or choose
another **Folder on the destinations**; the tool has no option to encrypt
the names.

## Where the secrets are

| Secret | Location | Protection |
|---|---|---|
| Passphrase | `/etc/proxdump/rclone.conf` (`password =` of the `…-crypt` sections) | File readable by root only (mode 600, folder 700) |
| Access tokens, S3 keys, SFTP password | Same file | Same |
| SSH key of the SFTP connection | `/etc/proxdump/sftp_key` | Mode 600 |

In `rclone.conf` the passphrase is *obscured*, not encrypted: rclone's
obscuring only prevents it from being read at a glance, and anyone who can
read the file can reveal it (`rclone reveal`). The protection is the
permission of the file, and therefore root access to the node.

**Configuration → Encryption → Display the passphrase** shows it again at
any time, on the plain terminal so that it can be selected and copied. Keep a copy outside the server (password manager, printed copy):
without it the backups cannot be decrypted by anyone, including by this
tool on a reinstalled server.

## What encryption does not cover

- **The local staging folder**: `vzdump` writes the archive there in clear;
  it is deleted once uploaded and verified. Anyone with access to that
  folder during the backup can read it.
- **The transport**: the connections to the destinations use HTTPS or SSH,
  independently of the encryption described here.
- **Changing the passphrase**: the backups already uploaded stay encrypted
  with the former one. The tool reads only one passphrase at a time, so the
  old backups become unreadable until the former passphrase is restored.

## Verification after upload

When *Verification after upload* is enabled (the default), the tool runs
`rclone cryptcheck`: it reads the nonce of the remote file, encrypts the
local archive again with it and compares the checksum of the result with the
one reported by the destination. This proves that what was stored is exactly
what was encrypted, without downloading it. On an SFTP server that offers no
checksum command, only the sizes can be compared; the log says so.

## Decrypting without proxdump

Any rclone can read the backups, given the passphrase and these settings:

```ini
[backups]
type = crypt
remote = <remote>:pve-backups/<node>
password = <output of: rclone obscure 'your passphrase'>
filename_encryption = off
directory_name_encryption = false
suffix = .encrypted
```

See [Disaster recovery](RECOVERY.md) for the complete procedure.
